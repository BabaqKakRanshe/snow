# Единая спецификация стиля для 3D-моделей Snow — исследование

Дата: 26.10.2026. Задача: один машиночитаемый файл стиля. По нему другой ИИ-агент строит модели в Blender (headless или через Blender MCP), а скрипт проверяет новые модели сам.

Что уже есть в проекте и что спецификация должна вобрать:
- `docs/gdd/PSX_STYLE_FOR_ENVIRONMENT.md` — рецепт PSX-текстуры, плотность текселей по классам, палитры, импорт в Unity.
- `tools/psx_texture_tool.py` — уменьшение, k-means палитра, дизеринг 4×4, `--contrast`, `--grain`.
- `tools/snow_qa/` — проверки и снимки (есть `sheet.py`, `shots.py`).

## 1. Как студии пишут арт-библии и технические спецификации

Ссылки:
- Lemonsky Studios, конвейер аутсорса арта — https://www.lemonskystudios.com/insights/game-art-outsourcing-pipeline — до первого заказа нужны четыре документа: стиль-гайд, техспецификация, схема работы, «критерии готовности». В техспецификации: движок, бюджет полигонов, плотность текселей, форматы и размеры текстур, экспорт, имена.
- Zatun, ошибки аутсорса — https://zatun.com/five-mistakes-that-could-kill-your-project/ — арт-библия: палитра, свет, пропорции, материалы, настроение. Отдельно — техническая библия. Обязательно примеры «как НЕ надо».
- GameDev.net, «Creating art bible / style guide» — https://gamedev.net/forums/topic/552212-creating-art-biblestyle-guide/4955332/ — список нужной графики с количеством, описание стиля, форматы файлов и имена.
- Valve, «Illustrative Rendering in Team Fortress 2» (NPAR/SIGGRAPH 2007) — https://www.advances.realtimerendering.com/s2007/Mitchell-IllustrativeRenderingInTF2(Siggraph07%20Course%20Notes).pdf — стиль описан как набор правил шейдинга и цвета, которые служат игре (читаемость силуэта, тон по командам).
- Valve, GDC 2008 «Stylization with a Purpose» — https://cdn.steamstatic.com/apps/valve/2008/GDC2008_StylizationWithAPurpose_TF2.pdf — причины стиля: геймплей, читаемость, бренд. Правила для силуэтов и пропорций.
- Arc System Works, GDC 2015 «Guilty Gear Xrd's Art Style» — https://www.ggxrd.com/Motomura_Junya_GuiltyGearXrd.pdf — стиль держится на жёстких технических правилах: нормали вручную, линии через UV, выравнивание текселей. Пример «стиль = правила, а не картинки».
- Dota 2 Workshop, требования к предметам (пересказ на Polycount) — https://polycount.com/discussion/comment/1598147 — публичный «лист бюджетов»: лимит треугольников на слот и LOD, общий бюджет текстур 1024×512, плотность как у героя. Официальная страница: dota2.com/workshop/requirements (не открылась).
- Khronos, Asset Creation Guidelines 2.0 — https://www.khronos.org/blog/introducing-asset-creation-guidelines-2.0-siggraph-2025 — открытые правила создания ассетов, живой документ, не привязан к пакету.

Лучшие практики:
- Делить на два документа: «стиль» (как выглядит) и «техника» (числа, бюджеты, имена, экспорт).
- Каждое правило — с числом и допуском, а не словами «примерно» или «в меру».
- Бюджеты — таблицей по классам ассетов (мелкий предмет, техника, здание, интерьер).
- Давать примеры «хорошо» и «плохо» рядом. Плохие примеры учат не меньше хороших.
- Ревью по этапам: болванка → детали → финал → проверка в движке. На каждом этапе — свой список проверок.
- Спецификация версионируется. Ассет помнит, по какой версии его сделали.

## 2. Машиночитаемые спецификации и автоматические проверки

Ссылки:
- W3C Design Tokens, Format Module 2025.10 (первая стабильная версия) — https://www.w3.org/community/reports/design-tokens/CG-FINAL-format-20251028/ — JSON-формат «токенов»: `$value`, `$type`, `$description`, `$extensions`, группы, ссылки `{group.token}`. Типы `color`, `dimension`, `number`. Файл `.tokens.json`.
- designtokens.org — https://designtokens.org/ — сайт формата, FAQ: стабильно, но ещё дорабатывается.
- Khronos 3DC Asset Validator — https://cdn.jsdelivr.net/npm/@mikefesta/3dc-validator@1.0.0/README.md — лучший готовый образец «требования в JSON → проверка». Поля: `model.triangles`, `materials`, `textures.width/height`, `requireDimensionsBePowersOfTwo`, `uvs.pixelsPerMeter {min,max}`, `uvs.requireNotOverlapping`, `uvs.requireNotInverted`, `uvs.gutterWidth`, `textures.pbrColorRange {30..243}`, `product.dimensions` с допуском в %. `-1` или `false` отключает проверку.
- Khronos glTF Asset Auditor — https://www.khronos.org/blog/khronos-gltf-asset-auditor — сравнивает свойства ассета с разрешёнными диапазонами.
- Unreal Data Validation, `EditorValidatorBase` — https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/EditorValidatorBase — валидатор решает, к чему он применим, и пишет «прошёл / упал / предупреждение». Можно на Python. Есть проверка при сохранении.
- Unity `AssetPostprocessor.OnPreprocessAsset` — https://docs.unity.com/en-us/engine/6000.7/script-reference/unityeditor/assetpostprocessor/onpreprocessasset — правила импорта задаются кодом при импорте.
- Unity Project Auditor — https://docs.unity3d.com/Manual/project-auditor/project-auditor-introduction.html — статический анализ, в том числе текстур и мешей.
- Пример проверки имён при импорте в Unity — https://github.com/SaiiPrashanth/Asset_Validator — PascalCase/snake_case, без пробелов.
- Pyblish — https://pyblish.readthedocs.io/ и https://github.com/pyblish/pyblish/wiki/End-User-How-it-works — схема «собрать → проверить → выгрузить → встроить». Выгрузка только если проверки прошли.
- NVIDIA Omniverse Asset Validator — https://docs.omniverse.nvidia.com/kit/docs/asset-validator/latest/source/extensions/omni.asset_validator.core/docs/rules.html — набор правил для USD, CLI, автоисправления. Правила вроде «объявить upAxis и metersPerUnit».
- Texel Density Checker для Blender (GPL) — https://extensions.blender.org/add-ons/texel-density-checker — считает плотность, подгоняет UV под цель, показывает цветом.
- SideFX Labs Texel Density — https://sidefxlabs.artstation.com/projects/8eJY0G — формула: пиксели / метр (512 px на 1 м = 512 px/m).
- Polycount, плотность текселей — https://polycount.com/discussion/comment/2608791 — держать одну плотность или немного классов. Разница около 10% глазом не видна.
- Blender, тесты рендера по эталонам — https://projects.blender.org/archive/blender-archive/raw/branch/main/tests/python/modules/render_report.py — эталонные картинки в `reference_renders`, сравнение через `idiff`, порог ошибки, HTML-отчёт «новое / эталон / разница».
- Blender, аргументы командной строки — https://docs.blender.org/manual/en/latest/advanced/command_line/arguments.html — `-b` (без окна), `--python`. Важно: `.blend` писать до `--python`.

Лучшие практики:
- Одно место правды — JSON. Текст для людей генерируется из JSON или ссылается на него, а не дублирует числа.
- Каждое числовое правило — диапазон `{min, max}` или цель с допуском `{target, tol_pct}`. Так сделано в 3DC Validator.
- Правило можно выключить (`-1` / `false`), не удаляя его.
- Наследование по классам: общие значения + переопределения для класса. В DTCG для этого есть `$extends` у групп и ссылки `{...}`.
- Каждая проверка имеет id, уровень (`error` / `warn`) и подсказку, как исправить.
- Отчёт проверки — тоже JSON. Агент читает его и чинит сам.
- Проверка в двух местах: в Blender до экспорта и в Unity при импорте. Это ловит ошибки экспорта.
- Схема самой спецификации (JSON Schema) не даёт агенту написать опечатку в ключе.

## 3. PS1 / PSX: железо и практики

Ссылки:
- psx-spx, GPU PlayStation — https://psx-spx.consoledev.net/graphicsprocessingunitgpu/ — первоисточник. Страница текстур 256×256 текселей. Цвет текстуры: 4 бит (16 цветов, CLUT), 8 бит (256 цветов), 15/16 бит прямой. Дизеринг блоками 4×4: к 8-битному цвету добавляется смещение от −4 до +3, потом цвет режется до 5 бит. «Текстурное окно» повторяет участок внутри страницы.
- Wikipedia, техническое описание PlayStation — https://en.wikipedia.org/wiki/PlayStation_technical_specifications — те же режимы цвета, VRAM 1024×512.
- Polycount, текстурная память PS1 — https://polycount.com/discussion/226167/ — как текстуры делят VRAM: 4-битная текстура занимает четверть места 16-битной.
- MenacingMecha, Godot PSX style demo — https://github.com/MenacingMecha/godot-psx-style-demo — практичные заметки: текстуры как можно меньше, без фильтрации и мип-мапов, постеризация до 15–16 бит, больше вершинного цвета, лишние рёбра против искажения аффинных текстур. Разрешения кадра 256×240, 320×240, 512×240.
- Kodrin, URP-PSX (Unity, Shader Graph) — https://github.com/Kodrin/URP-PSX — открытый PSX-эффект для URP: снап вершин, аффинные текстуры, дизеринг. Последний пуш май 2024, на URP 17 требует правок (https://itch.io/post/14460423).
- PSXEffects (Triple Axis) — https://tripleaxis.itch.io/psxeffects — коммерческий набор: снап вершин, аффинная деформация текстур.
- PSX Cycles (Blender) — https://superhivemarket.com/products/psx-cycles/docs — PSX-рендер в Blender: Bayer 4×4, аффинные текстуры. Полезно для ревью-рендеров прямо в Blender.
- BlenderNation, PS1-style lowres tutorial — https://www.blendernation.com/2024/02/13/ps1-style-lowres-tutorial/ — пример процесса low-poly + маленькая текстура.
- Lucas Pope, дизеринг в Return of the Obra Dinn (обзор) — https://www.alanzucconi.com/?p=10365 — экранный упорядоченный дизеринг «плывёт» при движении камеры. Дизеринг в текстуре такого не делает.
- Bayer 4×4, объяснение — https://barbegenerativediary.com/en/tutorials/ordered-dithering-bayer-in-processing/ — матрица порогов и её повтор по модулю координат.
- Ordered dithering под свою палитру — https://github.com/qroph/ordered-dithering — таблица поиска для произвольной палитры.
- Lospec, база палитр — https://lospec.com/palette-list — палитры старого железа и пиксель-арта. Источник для проверки «наша палитра похожа на эпоху».

Лучшие практики:
- PSX — это ограничения, а не фильтр. Записывать их числами: размер атласа, число цветов, шаг дизеринга, плотность.
- Наш выбор (по `PSX_STYLE_FOR_ENVIRONMENT.md`): дизеринг и палитра запечены в текстуру, не экранные. Это держит картинку стабильной при движении. Спецификация должна прямо это сказать.
- Палитра своя у каждого атласа (k-means, 64 цвета; интерьер 32), но общий тон — в спецификации диапазонами (оттенок, насыщенность, яркость).
- Размеры атласов — степени двойки, 256 и 512. Больше — только для надписей (1024).
- Фильтрация `Point`, мип-мапы по решению проекта. Записать в раздел импорта Unity.
- Снап вершин и аффинные текстуры — эффекты движка, не модели. В спецификации модели их нет, кроме правила «большие полигоны дробить, чтобы не плыло».
- Геометрия: мало треугольников, но достаточно рёбер на больших плоскостях. Мелкие детали — текстурой, а не геометрией.

## 4. Как держать ИИ-агента в стиле при процедурной генерации

Ссылки:
- SceneCraft (ICML 2024) — https://arxiv.org/abs/2403.01248 — агент пишет Blender-скрипты, проверяет рендер через VLM, а повторяющийся код складывает в общую библиотеку («library learning»).
- 3D-GPT — https://arxiv.org/abs/2310.12945 — агент не моделирует «с нуля», а подбирает параметры процедурных генераторов.
- LL3M (2025) — https://arxiv.org/abs/2508.08228 — несколько агентов пишут Blender-код, общий контекст кода, база знаний по Blender API (BlenderRAG), правки стиля и материалов по запросу.
- BlenderGym (CVPR 2025) — https://arxiv.org/abs/2504.01786 — даже сильные VLM слабее человека в простых правках Blender. Помогает цикл «сгенерировать → проверить», и часть вычислений выгодно отдать проверке.
- BlenderMCP — https://glama.ai/mcp/servers/@ahujasid/blender-mcp/tools/get_viewport_screenshot — выполнение Python в живом Blender и снимок вьюпорта. Аддон не стартует в `blender -b`, поэтому для автоматических проверок нужен отдельный headless-путь.

Лучшие практики:
- **Стиль как код, а не как текст.** Агент не пишет материалы, дизеринг и износ сам. Он вызывает функции общей библиотеки с параметрами из JSON. Текстом остаётся только «что строить».
- Библиотека — единственный путь к материалу, палитре, AO, износу и экспорту. Если агенту чего-то не хватает, функцию добавляют в библиотеку, а не пишут в скрипте модели (как в SceneCraft).
- Скрипт модели детерминирован: фиксированный `seed`, версия библиотеки и спецификации пишутся в метаданные ассета.
- **Эталоны (golden).** 3–5 моделей разных классов, принятых пользователем. Для каждой: `.blend`, текстуры, рендеры с фиксированных камер, замеренные метрики. Агент сравнивает новую модель с эталоном своего класса.
- **Сначала числа, потом глаза.** Порядок: схема → геометрия/UV/имена → текстура (палитра, плотность, яркость) → контактный лист рядом с эталоном → оценка VLM или человеком.
- **Контактный лист.** Одни и те же камеры (4 стороны + 3/4 сверху), один свет, один фон, рядом эталон того же класса, линейка 1 м. Тот же лист у всех моделей — сравнение честное.
- Отчёт проверки даёт агенту конкретные числа: «плотность 82 px/m, цель 56 ±10%». Агент чинит и запускает снова. Лимит итераций, потом — вопрос человеку.
- Короткий бриф для агента (1 страница) со ссылкой на JSON и списком «нельзя». Длинная проза в брифе размывает правила.

## 5. Рекомендуемый формат для Snow

### 5.1. Раскладка файлов

```
tools/snow_style/
  snow_style.json            главная спецификация (единственный источник чисел)
  snow_style.schema.json     JSON Schema для самой спецификации
  AGENT_BRIEF.md             1 страница для агента: порядок работы, команды, «нельзя»
  snowstyle/                 Python-библиотека для Blender (bpy), версия = meta.version
    spec.py                  загрузка JSON, наследование классов, ссылки {..}
    geo.py                   примитивы и операции low-poly, фаски, дробление больших граней
    uv.py                    развёртка, подгонка плотности, отступы, снап к пиксельной сетке
    material.py              единственный шейдер и слоты текстур
    bake.py                  AO в цвет, износ по правилам, запекание исходника 4–8x
    psx.py                   обёртка над tools/psx_texture_tool.py (размер, палитра, дизеринг)
    naming.py                имена объектов, материалов, текстур, файлов
    export.py                FBX для Unity, оси, масштаб, метаданные
  check/
    check_asset.py           headless: blender -b X.blend --python check_asset.py -- --class prop_small --report out.json
    checks_geo.py, checks_uv.py, checks_tex.py, checks_naming.py
    compare_golden.py        метрики против эталона класса
  render/
    contact_sheet.py         фиксированные камеры, свет, фон, линейка; эталон рядом
source/style_golden/         эталоны (в snow-art, через LFS)
  <class>/<asset>/  model.blend, textures/, renders/, metrics.json
Snow/Assets/Snow/Editor/StyleImport/   AssetPostprocessor: те же правила импорта из snow_style.json
```

Сначала проверить, что из `tools/snow_qa/sheet.py` и `tools/psx_texture_tool.py` можно взять как есть, чтобы не писать второй раз.

### 5.2. Разделы `snow_style.json`

Синтаксис: свой JSON, проверяемый JSON Schema. Из DTCG берём только приёмы: ссылки `{texel.env}`, `$description` у каждого правила, наследование групп. Числа — диапазоны `{min, max}` или `{target, tol_pct}`, как в 3DC Validator.

1. `meta` — версия спецификации (semver), версия Blender и Unity, дата, ссылки на документы (`PSX_STYLE_FOR_ENVIRONMENT.md`).
2. `units` — метры, оси Blender → Unity, масштаб экспорта, где точка опоры (центр основания).
3. `classes` — классы ассетов (`prop_small`, `prop_large`, `vehicle`, `building`, `interior`, `decal_text`, `terrain_tile`). Каждый класс переопределяет общие значения и указывает свой эталон.
4. `texel` — цель px/m по классам (окружение 48–64, обшивка 50, детали 60, интерьер 76–154, надписи 640–1750), допуск ±10%, правило «соседние ассеты в одной сцене — один класс плотности».
5. `atlas` — разрешённые размеры (256, 512; 1024 только `decal_text`), степени двойки, отступ острова в пикселях на размер, заполнение UV не ниже X%.
6. `palette` — режим `per_atlas_kmeans`, число цветов по классам (64; интерьер 32), цветовое пространство sRGB, вес насыщенных мелочей, общий тон диапазонами (оттенок, насыщенность, яркость), запрет чистых чёрного и белого, допустимый диапазон яркости (как `pbrColorRange` 30–243).
7. `dither` — матрица Bayer 4×4 (значения в файле), сила, режим (`naive` / `two`), где применяется (только в текстуре, не на экране), `contrast`, `grain`.
8. `ao` — запекается в цвет, сила, дистанция, число сэмплов.
9. `wear` — правила износа: по выпуклости (края), по впадинам (грязь), по высоте (снизу грязь, сверху снег), по материалу (ржавчина на металле). У каждого правила порог, сила, `seed`.
10. `materials` — один шейдер, список слотов (`BaseColor`, `MaskMap`), максимум материалов на объект и на ассет, правило «текстуры только из атласа».
11. `geometry` — бюджет треугольников по классам, минимальный размер детали (не меньше 2 текселей), максимальный размер грани без дробления, флэт или смус шейдинг, без n-гонов, без нулевых граней, масштаб применён, многообразность там, где нужна.
12. `uv` — диапазон 0–1, нет перекрытий (кроме помеченной зеркальной симметрии), нет вывернутых островов, острова на пиксельной сетке.
13. `naming` — регулярные выражения для файлов, объектов, мешей, материалов, текстур (`T_<Name>_BaseColor`), коллекций, коллайдеров и LOD.
14. `export` — FBX-настройки, применение трансформаций, что не экспортировать, метаданные (версия спецификации, `seed`, класс).
15. `unity_import` — фильтр `Point`, мип-мапы, сжатие, Max Size по классу, Read/Write. Это читает `AssetPostprocessor`.
16. `review` — камеры (углы, высота, FOV), свет, фон, разрешение, линейка, раскладка контактного листа, эталон рядом.
17. `checks` — список проверок: `id`, раздел, уровень (`error` / `warn`), порог, подсказка «как исправить», можно выключить.
18. `golden` — эталоны по классам: путь, кто и когда принял, замеренные метрики (плотность, число треугольников, средняя яркость, гистограмма палитры) и допустимое отклонение новой модели от них.
19. `forbidden` — короткий список «нельзя» с картинками-примерами: гладкий PBR, блестящий металл, чистый белый снег, мелкие детали геометрией, экранный дизеринг в текстуре.

### 5.3. Порядок работы агента

1. Прочитать `AGENT_BRIEF.md` и класс ассета в `snow_style.json`.
2. Написать скрипт модели только на функциях `snowstyle`.
3. Запустить `check_asset.py` headless, прочитать JSON-отчёт, исправить ошибки.
4. Собрать контактный лист рядом с эталоном класса.
5. Отдать лист и отчёт человеку. Новый эталон добавляет только человек.

### 5.4. Что решить пользователю перед стартом

- Где жить коду: `tools/snow_style/` (предложение) или в `source/`.
- Какие 3–5 существующих моделей сделать первыми эталонами.
- Нужна ли проверка в Unity при импорте сразу или позже.
